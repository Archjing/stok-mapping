# stok-mapping 长期技术栈演进方案

> 面向对象：项目维护者、系统架构设计者、后续产品化实现者
> 日期：2026-06-09
> 目的：在控制软件体量的前提下，为本项目从当前本地研究系统演进到 TUI / 桌面工作台 / 长期可维护产品形态提供技术栈建议与迁移路径。

---

## 1. 背景

当前项目已经具备以下事实基础：

- `phase0.cli` 已形成较完整的命令化接口。
- 本地研究主库、维护状态库、Markdown / CSV 报告体系已经成形。
- `T6.3` 维护编排器 V1 已有状态库、run id、shard 状态、日志路径和报告路径。
- 策略准入报告、因子诊断、数据健康检查已经具备结构化输出。

因此，后续技术栈演进不应以“推倒重写”为前提，而应遵循：

- 保留当前已验证的 Python 研究核心。
- 把新技术栈优先用于壳层、控制层、产品层和长期服务层。
- 把“体量小、部署轻、可维护”作为长期约束，而不是只追求语言或数据库更换。

---

## 2. 目标与约束

本方案同时服务两个目标：

1. 尽量控制软件体量。
2. 为未来接近 Notion / Obsidian 风格的本地桌面研究工作台预留路线。

关键约束：

- 不能打断当前 `Python + SQLite + CLI + reports` 主线。
- 不能为了“更现代”而牺牲当前研究链路可复现性。
- 新栈必须能够和本地文件、SQLite、报告目录、维护编排器和平共处。
- 数据库迁移不能只凭“听起来更快”，必须按实际数据模型和查询类型决策。

---

## 3. 总体结论

`Go`、`Rust`、`Node.js` 都可以纳入后期技术栈，但职责应明确分层，不建议单一语言替代当前全部系统。

推荐的长期方向是：

- 桌面壳：`Tauri`
- 前端 UI：`Svelte` 或 `Vue`
- 研究引擎：短中期继续 `Python`
- 后期控制平面 / 服务层：优先考虑 `Go`
- 数据层：事务型数据优先 `SQLite / PostgreSQL`，分析型查询引入 `DuckDB`

不推荐的路径：

- 现在就把整个 Python 研究核心重写成 Go 或 Rust
- 仅仅为了“可能更快”就把所有 SQLite 全量迁到 PostgreSQL
- 用 Node.js 重写数据研究和回测主逻辑

---

## 4. 语言栈建议

### 4.1 Python

结论：短中期必须保留。

原因：

- 当前量化研究、回测、因子诊断、策略准入、数据处理逻辑已经成型。
- `pandas`、现有 CLI、SQLite 读写和报告生成都已稳定工作。
- 若现在重写，会把精力从“策略有效性与数据治理”转移到“重建已有能力”。

适合继续承担：

- 回测和 walk-forward
- 因子诊断
- 策略准入
- 财务因子处理
- 报告生成
- 本地研究脚本和数据清洗

### 4.2 Go

结论：最适合后期做控制平面和长期后台服务层。

优点：

- 编译产物小，部署干净。
- 并发模型简单，适合调度、任务状态机、后台 worker。
- 很适合 `System Orchestrator`、本地 API、任务控制、日志状态查询等长期需求。
- 团队长期维护成本通常低于 Rust。

适合承担：

- `System Orchestrator`
- 任务调度和状态查询服务
- 桌面 UI 的本地 broker / API 服务
- 后台同步和任务编排

不建议承担：

- 第一批量化研究回测核心
- 需要快速迭代验证的策略实验逻辑

### 4.3 Rust

结论：适合作为桌面壳和局部高可靠模块的技术储备，但不建议现在作为主迁移语言。

优点：

- 产物小，性能高。
- 与 `Tauri` 天然契合。
- 适合需要强约束、强安全边界的本地能力层。

代价：

- 开发复杂度更高。
- 对当前 Python 项目来说，引入成本高于 Go。

适合承担：

- `Tauri` 桌面端后端壳层
- 局部系统级能力
- 未来若需要高可靠本地服务模块，可局部引入

不建议承担：

- 当前阶段整套业务重写

### 4.4 Node.js

结论：适合产品界面层，不适合替代当前研究核心。

优点：

- 与桌面 Web UI 技术栈兼容性高。
- 生态成熟，适合前端构建、桌面集成、状态展示。

限制：

- 不适合作为本项目量化研究和回测主引擎。
- 若直接承担策略研究主线，会和当前 Python 栈形成高成本重复。

适合承担：

- 前端构建工具链
- 桌面 UI 配套层
- 报告可视化和交互工作台

---

## 5. UI / 产品层建议

### 5.1 TUI 阶段

如果先做终端内工作台，建议：

- 第一版继续使用 Python 生态，例如 `Textual`
- 只做现有 CLI / SQLite / reports 的交互壳层

原因：

- 最小改动即可起步
- 可快速验证信息架构
- 不会提前引入完整桌面技术栈

### 5.2 桌面 UI 阶段

如果目标是接近 Notion / Obsidian 风格的本地研究工作台，推荐：

- `Tauri + Svelte`
- 备选：`Tauri + Vue`

不优先推荐：

- `Electron`

原因：

- 你明确在意软件体量。
- `Tauri` 更适合本地优先、文件密集、SQLite 密集、CLI 密集的项目。
- 现有系统天然适合“桌面壳 + 本地 broker + 研究引擎”的模式。

`Tauri` 更符合本项目的原因：

- 产物和运行资源相对更轻。
- 便于和本地文件、SQLite、日志、报告目录交互。
- 权限边界更容易收窄。
- 可在桌面端承接现代 UI，同时保留后端异构语言空间。

### 5.3 前端框架选择

推荐顺序：

1. `Svelte`
2. `Vue`
3. `React`

推荐理由：

- 目标是控制体量、减少前端复杂度。
- Notion / Obsidian 风格需要良好的布局、面板、命令面板、文档式界面，但不一定需要最重的生态。
- `Svelte` 和 `Vue` 更容易做出轻量、本地优先、状态清晰的桌面工作台。

## 6. 数据层建议

### 6.1 SQLite 的当前定位

当前 `SQLite` 仍然合理，而且不应被仓促替换。

它适合：

- 本地单用户研究
- CLI 驱动系统
- 事务型状态存储
- 报告和中间结果本地归档
- 可复制、可审计、可离线运行

### 6.2 PostgreSQL 的适用场景

`PostgreSQL` 可以迁，但应解决的是“并发和系统组织问题”，不是想当然的“速度问题”。

更适合它承担的数据：

- 维护编排器状态
- 账户、订单、对账、审计
- 关注个股、情报台账、研究任务元数据
- 多进程 / 多服务共享状态
- 长期需要更严格 schema 演进和查询治理的数据

`PostgreSQL` 的主要价值：

- 并发访问更稳
- 锁模型更成熟
- schema 演进更正规
- 可观测性更强
- 更适合本地服务化后的多模块访问

### 6.3 DuckDB 的必要性

如果目标是“提高本地分析查询速度”，比起直接把所有内容迁到 PostgreSQL，更应该考虑引入 `DuckDB`。

它更适合：

- 大表扫描
- 因子诊断
- 回测结果聚合
- 研究型统计查询
- 本地分析工作流

建议定位：

- `SQLite / PostgreSQL`：事务型、状态型、元数据型
- `DuckDB`：分析型、批处理型、聚合型

### 6.4 是否要迁 PostgreSQL

结论：可以规划，但不应当前立即迁。

推荐触发条件：

- 维护编排器已经演进为长期本地服务
- 桌面 UI 或本地 API 开始并发访问数据
- 多个模块需要共享状态且 SQLite 锁竞争开始成为真实瓶颈
- 账户、审计、情报、任务台账需要更强 schema 治理

## 7. 推荐长期组合

### 7.1 中短期推荐

```text
Python + SQLite + CLI + Reports
```

目标：

- 保持研究主线推进
- 不打断当前数据治理和策略研发
- 若需要交互壳层，优先做 Python TUI

### 7.2 中期推荐

```text
Tauri + Svelte/Vue
        ↓
Local Broker / Command Layer
        ↓
Python CLI / SQLite / Reports
```

目标：

- 建立现代本地桌面工作台
- 复用现有 CLI 和报告体系
- 不重写回测与研究核心

### 7.3 后期推荐

```text
Tauri + Svelte/Vue
        ↓
Go System Orchestrator / Local API
        ↓
Python Research Engine
        ↓
PostgreSQL + DuckDB + local files
```

目标：

- 前台是统一桌面工作台
- Go 承担长期控制平面和服务层
- Python 继续承担研究引擎
- PostgreSQL 管状态和元数据
- DuckDB 管分析

---

## 8. 分阶段迁移路径

### 阶段 A：保持主线稳定

- 保持 `Python + SQLite`
- 完成当前 `T2.x`、`T6.x` 主线
- 不做数据库大迁移
- 若需要交互增强，先做 TUI 原型

完成标准：

- 策略准入、维护编排器、daily brief、数据健康门禁继续稳定推进

### 阶段 B：建立桌面壳

- 引入 `Tauri + Svelte` 或 `Tauri + Vue`
- 首先只做只读控制台
- 通过 CLI / 文件 / SQLite / 本地 broker 读取现有系统状态

完成标准：

- 能浏览报告库
- 能查看维护状态
- 能查看策略准入结果
- 不重写核心业务

### 阶段 C：抽出控制平面

- 把 `System Orchestrator` 抽成独立本地服务层
- 优先考虑 `Go`
- 为桌面 UI 提供统一状态接口

完成标准：

- UI 不再散连各业务模块
- 高风险写操作统一经过控制平面

### 阶段 D：数据层分化

- 继续保留部分 SQLite
- 将需要多模块共享和并发访问的事务数据迁到 `PostgreSQL`
- 将研究分析聚合引入 `DuckDB`

完成标准：

- 数据职责清晰分层
- 锁竞争、查询性能和维护成本整体改善

---

## 9. 关键原则

- 不把“语言升级”误当成“系统升级”。
- 不用重写替代当前已稳定的 Python 研究主线。
- 不为了数据库迁移牺牲当前可复现和本地优先优势。
- 先做壳层，再做控制层，再做服务化，再做数据库分层。
- UI 永远是现有 CLI / reports / database 的入口，不是新的事实来源。

---

## 10. 最终建议

如果目标是“尽量控制软件体量，同时为未来 Notion 风格本地桌面工作台铺路”，最稳妥的长期路线是：

1. 现在继续 `Python + SQLite`
2. 第一代交互壳层优先做 TUI 或只读桌面壳
3. 正式桌面工作台首选 `Tauri + Svelte`
4. 长期控制平面优先考虑 `Go`
5. 数据层按职责分化为 `SQLite / PostgreSQL / DuckDB`，而不是一次性全部替换

一句话总结：

> 最优路线不是“把项目换成 Go/Rust/Node”，而是“保留 Python 研究核心，用 Tauri 做产品壳，用 Go 做长期控制层，用 PostgreSQL + DuckDB 做后期分层数据底座”。
