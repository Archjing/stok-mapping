# stok-mapping 最终产品总体架构重构方案

> 文档目标：定义 `stok-mapping` 的**最终产品蓝图**，不受当前 Phase 0 实现边界约束。  
> 设计依据：
> - `refdocs/papers/en/INDEX.md` 与 `refdocs/papers/cn/cn_INDEX.md` 索引的论文材料
> - `/reports/` 下的研究报告与变更日志
> - `DEVELOPMENT_PLAN.md` 当前主线与边界
> - Tushare 文档 `63 / 68 / 90` 所代表的目标能力

---

## 1. 先给结论

`stok-mapping` 的最终产品，不应被规划成“一个带回测的因子选股工具”，而应被规划成：

> **一个以 Tushare 为核心数据底座、以机器学习研究与组合构建为主引擎、以回测仿真和盘前研判为应用输出的量化研究与应用平台。**

它的终局不只是：

- 研究若干候选策略
- 输出观察池
- 生成盘前报告

而是要形成一个完整闭环：

```text
数据接入 → 数据治理 → 特征与标签工厂 → 机器学习研究 → 组合构建 → 回测执行仿真 → 风险解释 → 应用输出
```

这意味着：

- 当前 `Phase 0` 是重要基础，但只是底座的一部分；
- 未来产品核心会从“因子研究框架”扩展到“ML 驱动的量化平台”；
- 现有总体架构需要按终局目标重新分层，而不是在 `phase0/` 内持续堆叠逻辑。

---

## 2. 产品终局定位

### 2.1 最终产品是什么

最终的 `stok-mapping` 应被定义为一个：

- 面向 A 股为主场景
- 可纳入美股/港股/宏观/利率/情绪作为辅助输入
- 以机器学习研究和组合决策为核心
- 兼具研究、回测、解释、盘前输出能力
- 可逐步产品化为 Web/PWA/桌面端的量化应用平台

### 2.2 它不是什么

即便终局能力增强，它仍然不应被定义为：

- 自动交易系统
- 直接执行下单的交易终端
- 纯粹的 LLM 荐股产品
- 只会做单因子回测的脚本集合

### 2.3 终局角色划分

最终产品应同时承担四类角色：

1. **研究平台**：管理数据、特征、模型、实验和报告
2. **策略工厂**：持续产出和比较候选信号与组合方案
3. **仿真系统**：模拟账户、持仓、交易和风险表现
4. **应用输出层**：形成盘前研判、观察池、解释与可视化界面

---

## 3. 为什么必须重构总体架构

用户已经明确提出两类长期要求：

1. **论文与研究报告是产品开发的重要依据**  
   这要求项目从架构上支持“研究材料 → 策略假设 → 模型实验 → 组合验证 → 应用输出”的可追踪链路。

2. **未来需要具备 Tushare 文档 63 / 68 / 90 所述能力**  
   这意味着系统不仅要有行情和因子，还要有：
   - 模型训练与推理
   - 滚动式评估
   - 预测记录与结果回填
   - 组合分配
   - 账户/持仓/成交仿真

这两个要求叠加起来，直接说明：

> 未来架构不能继续只围绕“候选策略回测脚本”展开，而必须升级为“量化研究平台架构”。

## 4. 最终产品的总体分层

建议把最终产品重构成 8 层。

```text
┌──────────────────────────────────────────────────────────────┐
│ 8. Product & Delivery Layer                                 │
│ Dashboard / PWA / Desktop / Daily Brief / Watchlist         │
├──────────────────────────────────────────────────────────────┤
│ 7. Explanation & Decision Support Layer                     │
│ Risk narrative / Scenario analysis / LLM-assisted summary   │
├──────────────────────────────────────────────────────────────┤
│ 6. Backtest & Execution Simulation Layer                    │
│ Account / Positions / Orders / Fills / Costs / Replay       │
├──────────────────────────────────────────────────────────────┤
│ 5. Portfolio Construction & Risk Layer                      │
│ Weights / Constraints / Optimization / Exposure control     │
├──────────────────────────────────────────────────────────────┤
│ 4. ML Research & Signal Engine Layer                        │
│ Training / inference / rolling eval / factor-model hybrids  │
├──────────────────────────────────────────────────────────────┤
│ 3. Feature & Label Factory Layer                            │
│ PIT alignment / technical / fundamental / alt data / labels │
├──────────────────────────────────────────────────────────────┤
│ 2. Data Governance & Storage Layer                          │
│ Local DB / source audit / versioning / freshness / quality  │
├──────────────────────────────────────────────────────────────┤
│ 1. Multi-Source Ingestion Layer                             │
│ Tushare / AkShare / Tiingo / FRED / news / reports          │
└──────────────────────────────────────────────────────────────┘
```

这 8 层不是“为了漂亮而分层”，而是未来功能天然要求分层。

## 5. 每一层的终局职责

## 5.1 第 1 层：多源数据接入层

### 目标

解决“数据从哪里来，如何统一接入”的问题。

### 终局设计

以 **Tushare** 为国内市场核心主源，按数据类型做专业化接入：

- **国内股票主数据源**：Tushare
- **国内股票 fallback**：AkShare / 新浪快照 / 本地库
- **美股个股与 ETF 计划主源**：Tiingo
- **宏观/利率/VIX 计划主源**：FRED
- **`yfinance` 定位**：仅作为美股、ETF、宏观代理与 FX 研究输入的 fallback，不作为长期正式主源
- **港股/外资情绪代理**：Tushare / AkShare / 港股专门源
- **新闻/研报/文本语料**：Tushare 新闻类接口 + 本地归档

### 终局要求

这一层必须支持：

- 主源与 fallback 策略
- 批量 backfill
- 增量更新
- 按资产类别分 adapter
- 统一 symbol / date / frequency 规范
- 来源记录和质量审计

### 结构建议

```text
ingestion/
  a_share/
  us_market/
  macro/
  hk_market/
  text_data/
  adapters/
```

---

## 5.2 第 2 层：数据治理与存储层

### 目标

解决“如何让研究可复现、数据可审计、时间线不出错”的问题。

### 终局设计

本地数据库不应只是“缓存”，而应是正式的数据治理层。

需要管理的对象包括：

- 日线/分钟线/指数/ETF/宏观时间序列
- 财务报表与因子快照
- 新闻、研报、情绪文本索引
- 预测记录与回填结果
- 模型评估记录
- 账户/交易/持仓仿真记录

### 必备能力

- 数据版本管理
- freshness 检查
- source audit
- point-in-time 对齐
- symbol normalization
- 表级 schema 演进
- 研究运行快照留存

### 架构调整意义

当前 `a_share_history.sqlite` 是非常好的起点，但终局可能需要：

- 继续用 SQLite 作为本地研究库起步
- 中后期按需要升级为 DuckDB / PostgreSQL / ClickHouse 中的一种或组合

原则不是“先上重型数据库”，而是：

> 先保留本地研究可控性，再按数据规模和实验管理复杂度升级。

---

## 5.3 第 3 层：特征与标签工厂

### 目标

解决“机器学习模型到底吃什么、学什么”的问题。

这是从当前因子研究框架迈向 ML 平台最关键的一步。

### 终局职责

#### 特征工厂

支持统一生成：

- 技术面特征
  - 动量
  - 波动率
  - 换手率
  - 成交活跃度
  - 突破特征
  - K线行为
- 基本面特征
  - ROE
  - 营收增速
  - 利润增速
  - 现金流质量
  - 负债率
  - 估值因子
- 横截面特征
  - 行业相对强弱
  - 市值分层
  - 残差特征
  - 流动性分层
- 跨市场特征
  - 纳指/SOX/KWEB/VIX/CNH 等映射特征
- 文本/情绪特征
  - 研报情绪
  - 新闻摘要标签
  - 舆情强弱

#### 标签工厂

支持统一定义：

- next day up/down
- future k-day return
- rank label
- top-n inclusion label
- regime label

### 关键要求

- 所有特征和标签都必须遵守 **point-in-time** 约束
- 财务、文本等慢频数据必须有可用日期
- 训练集/验证集切分不能混用未来信息

### 结构建议

```text
features/
  technical/
  fundamental/
  cross_market/
  text/
labels/
  classification/
  regression/
  ranking/
```

---

## 5.4 第 4 层：机器学习研究与信号引擎层

### 目标

解决“如何从特征产生信号”的问题。

### 终局设计

这一层不应只容纳一个模型，而应支持多类研究范式共存：

#### A. 因子规则型

- baseline 策略
- MA/K 线规则
- 动量/反转/低波组合

#### B. 传统机器学习

- Logistic Regression
- SVM
- Random Forest
- XGBoost / LightGBM / CatBoost
- Lasso / Ridge / Elastic Net

#### C. 浅层神经网络

- MLP
- tabular deep models

#### D. 时序/结构化深度模型

- LSTM / TCN
- Transformer / StockMixer 类模型
- GNN / 图结构模型

### 终局职责

- 训练
- 推理
- 滚动更新
- 超参搜索
- 模型版本记录
- 预测结果持久化
- 评估指标生成

### 为什么这一层必须独立

Tushare doc 90 讲的是“从数据到模型训练预测”；
Tushare doc 68 讲的是“滚动评估、结果记录与组合分配”；
这说明模型层不能再只是 `walk_forward.py` 里的一个参数分支，而应成为独立子系统。

### 结构建议

```text
research/
  experiments/
  models/
  training/
  inference/
  evaluation/
  registry/
```

---

## 5.5 第 5 层：组合构建与风险层

### 目标

解决“预测不是投资组合，如何从信号走到组合”的问题。

这是 doc 68 对架构提出的关键补足。

### 终局职责

- 评分转权重
- top-n 等权 / 分数加权
- 风险预算
- 行业约束
- 单票权重约束
- 波动目标控制
- 回撤控制
- 可成交性约束
- Markowitz / 协方差风险建模
- 无法做空时的 long-only 权重归一化

### 终局要求

组合层必须和信号层分离。

原因是：

- 好模型不一定等于好组合
- 高预测准确率不等于高夏普
- 最终产品输出的是组合暴露，而不是单一股票分数

### 结构建议

```text
portfolio/
  allocators/
  optimizers/
  constraints/
  risk_models/
```

---

## 5.6 第 6 层：回测与执行仿真层

### 目标

解决“策略在账户层面到底会发生什么”的问题。

这是 doc 63 对当前架构的最大补课方向。

### 终局职责

- 账户资产净值
- 持仓
- 买卖记录
- 手续费 / 印花税 / 滑点
- 调仓日回放
- 再训练与再平衡时点
- 组合净值曲线
- 交易日志
- 策略 replay

### 为什么要独立成层

当前项目已有 walk-forward，但更偏“策略收益计算层”。
终局产品需要的是“账户级仿真层”。

两者差异在于：

- walk-forward 关注策略是否有效
- execution simulator 关注账户如何演化

### 结构建议

```text
backtest/
  accounts/
  brokers/
  fills/
  replayers/
  ledgers/
```

---

## 5.7 第 7 层：解释与决策辅助层

### 目标

解决“结果如何被人读懂并用于决策”的问题。

### 终局职责

- 候选策略胜出原因解释
- 风险暴露说明
- 情景推演
- 主策略失效条件
- 盘前摘要
- 观察池理由
- 人工决策支持

### LLM 的正确位置

LLM 可以进入这一层，但不应直接替代：

- 特征工厂
- 模型训练层
- 组合优化层
- 回测仿真层

它适合做：

- 研究摘要
- 报告生成
- 文本结构化
- 解释层组织
- 风险语言整理

也就是：

> LLM 是解释器和研究助手，不是主 alpha 生成器。

---

## 5.8 第 8 层：产品与交付层

### 目标

解决“这个平台最终以什么形式被使用”的问题。

### 终局输出形态

- 每日盘前报告
- 观察池
- 候选比较面板
- 策略评估报表
- 风险监控看板
- Web Dashboard
- PWA
- 桌面端封装

### 最终产品使用者视角

最终用户看到的不是：

- SQLite 表
- walk-forward CSV
- 零散脚本

而是：

- 今日策略状态
- 观察池
- 风险等级
- 为什么这些票入选
- 当前模型是否可信
- 当前组合是否过于集中或风险过高

因此，应用层的核心价值是“把复杂研究链路压缩成可消费结果”。

## 6. 当前架构中哪些可保留，哪些必须调整

## 6.1 可以保留的部分

当前项目里，以下资产可以直接进入终局平台：

1. **本地历史库思路**  
   这是未来数据治理层的核心雏形。

2. **数据时效保护与来源审计思路**  
   这是平台级能力，不只是 Phase 0 临时逻辑。

3. **股票池构建链路**  
   未来仍是 Feature/Portfolio 层的前置环节。

4. **walk-forward 评估思想**  
   未来仍会保留，但应沉入更正式的 research/backtest 体系。

5. **effectiveness gate 机制**  
   应保留，并升级为统一实验准入体系。

6. **报告输出体系**  
   可演化成产品交付层的一个子能力。

## 6.2 必须调整的部分

### 1. `phase0/` 单目录承载过多职责

当前 `phase0` 同时承担：

- 数据接入
- 特征构造
- 策略逻辑
- 回测
- 报告

终局必须拆分。

### 2. 机器学习能力不能作为 walk-forward 内嵌分支

ML 需要独立的：

- dataset builder
- trainer
- evaluator
- prediction logger
- model registry

### 3. 组合层必须显式化

从论文和 Tushare doc 68 来看，评分层和权重层必须分开。

### 4. 执行仿真必须从“收益计算”升级为“账户仿真”

这是 doc 63 对项目的直接要求。

## 8. 新的阶段路线图

## Phase A：研究底座完成期

目标：把当前 Phase 0 升级为更稳的数据与实验底座。

### 核心任务

- 稳定 Tushare 主源
- 完善本地数据治理
- 明确 point-in-time 规则
- 继续保留候选比较链路
- 整理研究文档与报告到统一证据链

### 验收标准

- 数据层可复现
- 研究层可复跑
- 报告层可追踪

---

## Phase B：特征与标签工厂期

目标：建立机器学习研究前置层。

### 核心任务

- 抽离技术面特征生成器
- 抽离基本面 PIT 特征生成器
- 建立标签构建逻辑
- 建立数据集切分与滚动窗口定义

### 产物

- feature tables
- label tables
- dataset builder

---

## Phase C：ML 研究引擎期

目标：让项目正式具备机器学习量化研究能力。

### 核心任务

- 接入 sklearn 基线模型
- 建立统一训练/验证流程
- 记录预测与实际结果
- 输出 precision / recall / F1 / Sharpe / OOS 等评估
- 建立实验版本记录

### 第一批建议模型

- Logistic Regression
- SVM
- Lasso / Ridge / Elastic Net
- Random Forest / XGBoost 类树模型

### 原则

先上稳妥基线，再上深度模型。

---

## Phase D：组合与风险层期

目标：从“预测能力”走到“可投资组合能力”。

### 核心任务

- 建立评分到权重的映射
- 支持等权、分数加权、风险预算
- 引入协方差 / 风险约束
- 做行业、单票、流动性约束

### 对应来源

这一步是对 Tushare doc 68 能力的正式吸收。

---

## Phase E：账户级回测仿真期

目标：正式建立账户/持仓/成交仿真系统。

### 核心任务

- 账户状态对象
- 订单与成交对象
- 仓位与现金演化
- 成本模型
- 调仓 replay

### 对应来源

这一步主要吸收 Tushare doc 63 的能力方向。

---

## Phase F：解释与应用化输出期

目标：把平台结果交付给人。

### 核心任务

- 盘前日报产品化
- 观察池解释模板
- 风险场景说明
- Dashboard / PWA / 桌面端
- LLM 进入解释辅助层

## 2. 整合原则

后续整合必须遵守以下原则：

### 2.1 不轻易删除旧版已做好的功能规划

旧版计划书中已经明确的产品能力，应默认继续保留，包括：

- A 股盘前情景推演
- 观察池
- 风险暴露说明
- 信号等级体系
- 本土主因子排序
- 跨市场风险/情绪 overlay
- 候选 compare / gate / report 输出
- 报告化交付思路

### 2.2 新版蓝图只能作为补充展望逐步吸收

新版蓝图中提出的更重架构能力，不应直接推翻当前应用导向主线，而应作为：

- 中长期扩展方向
- 架构拆分储备
- ML 与回测仿真升级方向
- 后续模块化演进依据

### 2.3 平台化改造必须服务于产品可用性

任何新增层次、目录拆分或中后台重构，都应回答一个问题：

> 它是否有助于更快、更稳地形成一个可应用的产品？

如果答案是否定的，就不应优先实施。
