# 网络主题调研与参考资料归档流程

> 适用范围：凡是通过网络搜索、公开网页、平台文档、论文、博客或新闻资料得出项目结论的工作，都必须按本流程执行。  
> 目标：每次调研都留下可复查的来源、摘要、采信理由和项目结论，避免结论只停留在对话里。

## 1. 触发条件

出现以下任一情况时，必须执行本流程：

- 用户要求“全网搜索”“查资料”“找依据”“主题调研”“形成结论”。
- 结论会影响项目参数、策略假设、数据源选择或开发优先级。
- 需要引用第三方文档、交易平台说明、监管规则、论文或市场资料。
- 信息具有时效性，存在政策、费率、接口、平台规则变化风险。

## 2. 标准步骤

### Step 1：明确调研问题

先把问题压成一句可验证的问题，例如：

```text
普通个人 A 股交易者用于回测的合理滑点参数是多少？
```

同时记录适用边界：

- 市场：A 股 / 美股 / 港股 / 跨市场
- 对象：个人交易者 / 机构 / 策略研究 / 实盘模拟
- 时间：当前日期和资料发布日期
- 约束：普通网络、普通软件、普通交易权限等

### Step 2：搜索与来源分层

优先级从高到低：

1. 官方文档或监管规则
2. 主流量化平台文档
3. 券商、交易系统或交易软件说明
4. 学术论文或行业研究
5. 高质量技术博客或解释性资料

每个来源必须记录：

- 标题或来源名称
- 原始链接
- 发布方
- 资料类型
- 访问日期
- 与本项目问题的关系

### Step 3：提取摘要，避免全文搬运

归档文档只保留：

- 关键观点摘要
- 与项目参数或判断相关的短摘录
- 可采信点
- 局限性

不要把网页全文复制进项目。对版权页面，必须使用摘要和短摘录。

### Step 4：形成项目内结论

结论必须和项目场景绑定，不能只复述资料。

结论至少包括：

- 推荐值或推荐区间
- 适用场景
- 不适用场景
- 是否需要敏感性测试
- 是否需要进入开发计划或任务清单

### Step 5：生成归档文档

每次调研都在 `refdocs/` 下生成一份 Markdown。

文件命名建议：

```text
refdocs/<topic>_sources.md
```

示例：

```text
refdocs/slippage_assumption_sources.md
```

文档必须包含以下结构：

```markdown
# <主题>来源整理

> 生成日期：
> 调研问题：
> 项目结论：

## 1. 工具与搜索记录

## 2. 参考来源

### 2.1 <来源名称>

- 原始链接：
- 发布方：
- 资料类型：
- 访问日期：
- 摘要：
- 可采信点：
- 局限性：
- 项目内解读：

## 3. 聚合结论

## 4. 对项目的影响

## 5. 后续待验证事项
```

### Step 6：必要时更新项目计划

如果调研结论改变了项目方向，必须同步更新：

- `DEVELOPMENT_PLAN.md`
- `refdocs/todo/WEEKLY_EXECUTION_CHECKLIST.md`
- 相关策略解释文档或参数说明

如果只是旁路资料归档，不进入主线计划，也要在归档文档中说明。

## 3. 质量标准

一份合格调研报告必须满足：

- 至少有 2 个独立来源，除非用户明确只要求单一来源。
- 明确区分“资料原文含义”和“项目内推断”。
- 原始链接完整保留。
- 摘要能让读者不打开网页也理解采信依据。
- 结论有边界条件，不把研究假设包装成确定事实。
- 若工具失败，必须记录失败方式和 fallback 方法。
